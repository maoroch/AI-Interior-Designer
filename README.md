Веб-платформа: пользователь загружает план квартиры/дома → мультиагентная AI-система строит 2D/3D-модель помещения и автоматически создаёт функциональный дизайн интерьера, с которым можно взаимодействовать через чат на естественном языке и редактировать в реальном 3D-пространстве.

## Стек

| Слой | Технологии |
|---|---|
| Frontend | Next.js 15 (App Router), TypeScript, Tailwind CSS, Zustand |
| 3D | Three.js, React Three Fiber, Drei |
| Backend | FastAPI (async), Pydantic v2 |
| Очереди задач | Taskiq + Redis (брокер и result backend) |
| База данных | MongoDB (Motor, async-драйвер) |
| Файловое хранилище | S3-совместимое (MinIO локально, R2/S3 в проде) |
| LLM | Groq API (текстовые агенты + vision-модель для валидации плана) |
| CV | OpenCV (MVP-эвристики) → в перспективе модель сегментации на базе CubiCasa5K |

## Почему такой стек (коротко)

- **FastAPI + Taskiq + Redis** — мультиагентный пайплайн — это по сути цепочка
  асинхронных задач с разной длительностью. Taskiq даёт очередь с
  чекпоинтами (см. ниже) без необходимости писать собственный оркестратор.
- **MongoDB** — сцена (`Scene`) — документ с вложенными списками
  переменной структуры (комнаты, мебель, свет, декор). Реляционная схема
  для этого была бы куда многословнее без реальной пользы, т.к. сцена
  всегда читается/пишется целиком по `project_id`.
- **Groq** — низкая задержка LLM-инференса критична, т.к. пользователь ждёт
  ответа в реальном времени и в анкете, и в чате.
- **Three.js/R3F** — стандарт для интерактивной 3D-визуализации в браузере;
  Drei даёт `OrbitControls` и другие примитивы "из коробки".

## Архитектура мультиагентной системы

Полный пайплайн разбит на **два Taskiq-таска**, а не на один сплошной —
из-за Architect Agent, после которого пайплайн обязан остановиться и
дождаться решения пользователя:

```
┌─────────────────────── run_analysis_pipeline ───────────────────────┐
│ Upload (PNG/JPG)                                                     │
│   → Floor Plan Analyzer   (CV-сегментация + LLM-валидация размеров)  │
│   → Room Detector         (LLM классифицирует тип каждой комнаты)   │
│   → Architect Agent       (предлагает 1-2 варианта перепланировки)  │
│ Сцена v1 сохраняется в Mongo, статус → awaiting_architect_decision   │
└───────────────────────────────────────────────────────────────────────┘
                              │
                    пользователь выбирает
                    вариант / "как есть"
                              │
┌─────────────────────── run_design_pipeline ─────────────────────────┐
│   → Architect Agent.apply_suggestion  (если выбран вариант —        │
│                                         пересчитывает полигоны)      │
│   → Interior Designer     (стиль, материалы, цвета по комнатам)     │
│   → Furniture Planner     (подбор + расстановка мебели-примитивов)  │
│   → Lighting Designer     (потолочный + акцентный свет)             │
│   → Decorator             (ковры, растения)                         │
│   → Scene Generator       (сборка финального Scene)                 │
│ Сцена vN сохраняется, статус → ready                                 │
└───────────────────────────────────────────────────────────────────────┘

Conversation Agent — не часть линейного пайплайна. Читает последнюю версию
сцены + реплику из чата, возвращает точечные патч-операции
(add/update/remove над furniture/decor/lighting), которые применяются
без пересчёта всего пайплайна. Каждый патч — новая версия сцены (version++).
```

Такое разбиение — это и есть "чекпоинт": если пользователь просто меняет
пожелания в анкете, не нужно заново гонять CV и Architect Agent — они уже
закреплены в сцене v1.

### Уникальная особенность — Architect Agent

В отличие от типового "AI-декоратора", Architect Agent в этом проекте умеет
менять саму геометрию — предлагать объединение комнат, перенос
ненесущих перегородок и т.п., причём в MVP это работает полноценно: выбор
пользователя реально пересчитывает полигоны комнат (`app/agents/architect/agent.py`),
а не просто возвращает текстовое описание.

## Схема сцены (центральный контракт)

`backend/app/models/scene.py` — единственный источник истины. Frontend
дублирует эти типы вручную в `frontend/lib/types.ts` (см. комментарий там же).

```jsonc
{
  "project_id": "proj_...",
  "version": 3,
  "rooms": [
    {
      "id": "room_1", "type": "kitchen",
      "polygon": [[0,0], [4,0], [4,3], [0,3]], "height": 2.7,
      "walls": [{ "id": "wall_1", "start": [0,0], "end": [4,0],
                  "thickness": 0.2,
                  "openings": [{ "type": "door", "position": 0.5, "width": 0.9 }] }],
      "floor_material": "oak_wood", "wall_color": "#E8E4DD"
    }
  ],
  "furniture": [
    { "id": "f_1", "room_id": "room_1", "type": "sofa",
      "position": [1.5, 0, 1.0], "rotation_deg": 90,
      "dimensions": [2.1, 0.85, 0.9], "material": "grey_fabric", "model_ref": null }
  ],
  "lighting": [{ "id": "l_1", "type": "ceiling", "position": [2,2.6,1.5],
                 "color_temperature_k": 3000, "intensity": 0.9 }],
  "decor": [{ "id": "d_1", "type": "plant", "position": [3.5,0,2.5] }],
  "architect_suggestions": [
    { "id": "opt_a", "title": "Объединить кухню с гостиной", "description": "...", "rooms_after": null }
  ],
  "architect_choice": null,
  "style": "Modern Minimalism"
}
```

`model_ref: null` означает, что предмет рендерится параметрическим боксом
(см. ниже) — это осознанное решение MVP, не баг.

## Мебель: примитивы вместо каталога (осознанное решение MVP)

Furniture Planner подбирает через LLM тип/материал/габариты мебели и
расставляет её простой эвристикой (вдоль периметра комнаты, с отступом от
дверных проёмов и минимальным проходом 0.6м). Рендерится это как
параметрический бокс нужного размера и цвета — без визуального каталога
и без 3D-моделей.

Это разделяет две независимые по сложности задачи: "правильно ли
расставлена мебель" (эргономика, проходы) и "красиво ли она выглядит"
(3D-ассеты). **Фаза 2**: заменить примитивы на курируемую библиотеку GLTF-
моделей (категория × стиль), подключаемую через уже существующее поле
`model_ref` — рендер-компонент (`SceneViewer.tsx`) специально спроектирован
так, чтобы эта замена не потребовала переписывать логику остальных агентов.

## CV для распознавания плана — временная эвристика

`backend/app/cv/segmentation.py` сейчас использует OpenCV-контуры
(`findContours` + `approxPolyDP`) — этого достаточно, чтобы пайплайн
работал end-to-end на простых планах, но недостаточно для точного
распознавания реальных чертежей.

**Известные open-source ориентиры для продакшен-версии:**
датасет **CubiCasa5K** (5000 размеченных финских планов: стены/комнаты/
двери/окна) и модели на его основе (U-Net/DeepLabV3+ с ResNet-энкодером).

⚠️ **Важно перед использованием готовых весов в продакшене**: часть
публичных репозиториев с предобученными весами CubiCasa5K распространяется
с **non-commercial-only** лицензией на конкретную сборку весов. Перед
переходом с MVP-эвристики на реальную модель — явно проверить лицензию
конкретного источника весов, либо переобучить модель на самом датасете
(его лицензия на переобучение — отдельный вопрос, тоже стоит перепроверить).

## API

| Метод | Путь | Описание |
|---|---|---|
| POST | `/projects/upload` | Загрузить PNG/JPG плана (лимит 15MB) → создать проект → запустить анализ |
| POST | `/projects/{id}/preferences` | Сохранить анкету пользователя (стиль, бюджет, семья, питомцы...) |
| POST | `/projects/{id}/architect-choice?choice_id=` | Выбрать вариант перепланировки (без параметра — "как есть") → запустить генерацию вариантов дизайна A/B/C |
| GET | `/projects/{id}` | Статус проекта (`PipelineStage`, `active_variant_id`) |
| GET | `/projects/{id}/scene` | Последняя версия сцены АКТИВНОГО варианта |
| GET | `/projects/{id}/scenes` | Последние версии ВСЕХ вариантов дизайна (A/B/C) |
| POST | `/projects/{id}/select-variant?variant_id=` | Сделать вариант активным (для просмотра и чата) |
| PATCH | `/projects/{id}/scene/furniture/{furniture_id}` | Прямое изменение мебели из 3D-UI (drag&drop позиции, материал/цвет) |
| POST | `/projects/{id}/chat` | Отправить реплику в AI-чат → патч сцены активного варианта |
| GET | `/projects/{id}/chat` | История чата |
| GET | `/projects/{id}/export/pdf?variant_id=` | Скачать PDF-отчёт (план, список мебели, смета) |
| WS | `/ws/projects/{id}` | Push-уведомления о смене стадии/готовности варианта (через Redis pub/sub) |

## Известные ограничения MVP (сознательные упрощения)

- CV-детекция стен — эвристика на bounding-box пикселей стен, не нейросеть;
  комната аппроксимируется прямоугольником (см. докстринг
  `app/cv/segmentation.py` — почему выбран именно такой подход, а не
  произвольный многоугольник через контуры). Многокомнатные планы пока не
  разбиваются на отдельные комнаты.
- Двери и окна детектируются (эвристика на разрывах линии стены,
  классификация по ширине — грубая, см. докстринг) и реально вырезаются
  в 3D-рендере стены (окна дополнительно получают полупрозрачную вставку).
  Проверено end-to-end тестами (`tests/test_segmentation.py`).
- Масштаб плана (`pixels_per_meter`) захардкожен, не извлекается из
  аннотаций/масштабной линейки на изображении.
- Мебель — параметрические боксы, не 3D-модели (см. раздел выше про
  осознанный выбор в пользу примитивов на MVP-этапе).
- Furniture Planner использует упрощённый алгоритм расстановки (bounding
  box комнаты + периметр), не полноценный constraint-solver; на
  непрямоугольных комнатах будет давать неточный результат.
- Architect Agent ограничен типовыми сценариями перепланировки (объединение
  комнат, увеличение за счёт соседней), не решает произвольную задачу.
- **Генерация нескольких вариантов дизайна** (A — выбранный стиль, B —
  Japandi, C — Luxury) реализована (`DESIGN_VARIANTS` в `pipeline_tasks.py`),
  варианты генерируются ПАРАЛЛЕЛЬНО через `asyncio.gather` (независимые
  документы в Mongo — безопасно); переключение между ними на фронтенде —
  `VariantSwitcher`.
- **Ретраи для LLM-вызовов** реализованы (`app/core/llm.py`, экспоненциальный
  backoff, 3 попытки), ошибки после исчерпания попыток теперь видимы
  пользователю (проект переходит в статус `failed` с текстом ошибки) вместо
  тихого проглатывания.
- **Тесты** есть (`backend/tests/`, 19 тестов, только чистая логика без
  сети/LLM: сегментация, расстановка мебели, патчи чата, сборка сцены,
  ретраи), запускаются в CI (`.github/workflows/ci.yml`) вместе со сборкой
  фронтенда. LLM-зависимые части (интерпретация чата, подбор мебели через
  Groq) не покрыты — требуют мока или интеграционных тестов с реальным
  ключом, это TODO.
- **Prod Dockerfile для фронтенда** есть (`frontend/Dockerfile`,
  multi-stage, standalone-сборка Next.js); для локальной разработки
  используется `frontend/Dockerfile.dev` (hot-reload).
- **Лимиты на upload** реализованы: максимум 15MB, проверка через Pillow,
  что файл — валидное изображение (а не файл с поддельным content-type),
  ограничение на разрешение (защита от decompression-bomb).
- **Walk-режим камеры** реализован (`PointerLockControls` + WASD,
  переключатель в `SceneViewer.tsx`) с базовыми коллизиями о стены:
  камера считается кругом радиусом 0.3м, движение по X и Z проверяется
  отдельно (осевое скольжение — можно идти вдоль стены, не залипая), сами
  стены-препятствия строятся из тех же сегментов, что и рендер (с вырезанными
  проёмами — через дверь пройти можно). Это упрощённая, не честная физика
  (нет наклонных столкновений, нет мебели как препятствия) — достаточно для
  MVP-ощущения "прогулки по дому".
- **Drag-and-drop мебели и смена материала через UI** реализованы (клик —
  выбор + панель материалов, перетаскивание — по плоскости пола); поворот
  мебели через UI пока не добавлен (только через чат).
- **PDF-экспорт** реализован (`GET /projects/{id}/export/pdf`): 2D-схема
  планировки сверху (не полноценный 3D-рендер — это отдельная более тяжёлая
  задача, вынесена в Фазу 2), таблица мебели по комнатам, ориентировочная
  смета по фиксированным ценам за категорию (не привязана к реальным
  поставщикам, см. докстринг `pdf_export.py`). Кириллица рендерится через
  встроенный в репозиторий шрифт DejaVu Sans (свободная лицензия) — стандартные
  шрифты reportlab (Helvetica) не содержат кириллических глифов, без этого
  весь русский текст в PDF отображался бы чёрными прямоугольниками
  (обнаружено и исправлено в процессе разработки, см. `app/export/fonts/`).
- Промпты ни разу не гонялись на реальном Groq API-ключе — не исключены
  сюрпризы в парсинге JSON-ответов (ретраи снижают риск, но не устраняют
  полностью).
- Нет авторизации, оплаты, каталога мебели — сознательно вне периметра MVP
  по ТЗ.
