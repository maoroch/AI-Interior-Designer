# Реестр заглушек и упрощений — что заменять

Единый список всего, что в проекте сделано как временная заглушка/эвристика/
хардкод, а не полноценная реализация. Для каждого пункта: где лежит, что
именно упрощено, почему, и что нужно сделать для полноценной версии.
Сгруппировано по областям, внутри — примерно по приоритету.

---

## 1. Компьютерное зрение (распознавание плана)

### 1.1 Комната = прямоугольник, не произвольный многоугольник
**Где:** `backend/app/cv/segmentation.py`, функция `segment_floor_plan`
**Что упрощено:** комната аппроксимируется `cv2.boundingRect` по пикселям
стен вместо честного многоугольника.
**Почему так:** попытки восстановить произвольный полигон через
`findContours`/`approxPolyDP` ломались на разрывах (двери/окна) — контур
"утекал" в разрыв (задокументировано в докстринге модуля, там же история
неудачных попыток: изотропное замыкание, направленное замыкание — оба дали
артефакты).
**Чем заменить:** обученная модель сегментации (см. п. 1.3) вместо
геометрических эвристик — она устойчива к разрывам по построению.

### 1.2 Многокомнатные планы не разделяются
**Где:** `backend/app/cv/segmentation.py`, `segment_floor_plan`
**Что упрощено:** `RETR_EXTERNAL`-подобный подход берёт только один внешний
контур/bounding box — весь план распознаётся как ОДНА комната.
**Чем заменить:** сегментационная модель, которая размечает каждую комнату
отдельным классом/instance (см. п. 1.3).

### 1.3 CV-эвристики вместо обученной модели (корневая причина 1.1 и 1.2)
**Где:** `backend/app/cv/segmentation.py` целиком
**Что упрощено:** bounding-box по порогу яркости пикселей вместо нейросети.
**Чем заменить:** U-Net/DeepLabV3+, обученная на датасете в духе CubiCasa5K.
⚠️ Перед использованием готовых весов — проверить лицензию (часть публичных
реализаций CubiCasa5K распространяется non-commercial-only) либо
переобучить самостоятельно.
**Сигнатура функции `segment_floor_plan(image_bytes) -> SegmentationResult`
менять не нужно** — замена изолирована от остального пайплайна.

### 1.4 Детекция дверей/окон — эвристика по ширине разрыва
**Где:** `backend/app/cv/segmentation.py`, `_detect_openings`,
константа `DOOR_MAX_WIDTH_M = 1.3`
**Что упрощено:** разрыв в стене шире 1.3м считается окном, уже — дверью.
Никакого распознавания символа дуги открывания (дверь) или двойной линии
(окно), которые реально рисуют на чертежах.
**Чем заменить:** та же обученная модель (п. 1.3), которая различает эти
символы напрямую.

### 1.5 Масштаб плана захардкожен
**Где:** `backend/app/cv/segmentation.py`, `pixels_per_meter = 50.0`
(используется в двух местах — `segment_floor_plan` и `SegmentationResult`)
**Что упрощено:** масштаб "50 пикселей = 1 метр" — фиксированное число, не
извлекается из масштабной линейки или текстовых аннотаций на самом плане.
**Чем заменить:** OCR/LLM-vision, читающий аннотации размеров на плане
(частично намечено в п. 2.3), либо явный ввод масштаба пользователем.

### 1.6 Пороговые константы CV подобраны на глаз
**Где:** `backend/app/cv/segmentation.py`:
`WALL_INTENSITY_THRESHOLD = 200`, `MIN_OPENING_WIDTH_M = 0.5`,
`MAX_OPENING_WIDTH_M = 3.0`, `MAX_OPENING_FRACTION_OF_WALL = 0.85`
**Что упрощено:** значения подобраны на синтетических тестовых планах
(`tests/test_segmentation.py`), не откалиброваны на реальных отсканированных
чертежах разного качества.
**Чем заменить:** калибровка на реальном наборе планов, либо снова —
обученная модель, для которой такие пороги не нужны.

## 2. LLM-агенты

### 2.1 Groq vision не используется вообще
**Где:** `backend/app/agents/floorplan_analyzer/agent.py`, конец функции
`analyze` — комментарий `# TODO: LLM-валидация через Groq vision`
**Что упрощено:** в конфиге (`groq_vision_model` в `config.py`) модель
прописана, но никто её не вызывает — валидация CV-результата через
vision-модель не реализована, это просто TODO-комментарий.
**Чем заменить:** реальный вызов `groq_vision_model` с изображением плана,
сверяющий результат CV и проставляющий размеры/уточняющий проёмы.

### 2.2 Architect Agent — типовые сценарии, не произвольная перепланировка
**Где:** `backend/app/agents/architect/agent.py`, весь модуль, особенно
`apply_suggestion`
**Что упрощено:** LLM просят выбрать из типовых сценариев (объединить
комнаты, увеличить за счёт соседней) и пересчитать полигоны текстовым
JSON-ответом — "грубая, но рабочая версия" (цитата из кода, строка ~64),
без честной геометрии (например, через `shapely`).
**Чем заменить:** после того как LLM выбрал сценарий — пересчитывать
полигоны детерминированным геометрическим кодом (union/split через
`shapely`), а не просить LLM угадать координаты.

### 2.3 Furniture Planner — bounding box комнаты, не полигон
**Где:** `backend/app/agents/furniture_planner/agent.py`, `_room_bbox`,
`_place_along_perimeter`
**Что упрощено:** расстановка мебели считается по прямоугольной
bounding-box комнаты. На непрямоугольных комнатах (когда п. 1.1 будет
исправлен) даст неверный результат — мебель может оказаться "за пределами"
реальной комнаты, если та не прямоугольная.
**Чем заменить:** point-in-polygon проверки вместо bbox, когда комнаты
перестанут быть только прямоугольниками.

### 2.4 Furniture Planner — эвристика расстановки, не solver
**Где:** `backend/app/agents/furniture_planner/agent.py`, константы
`MIN_CLEARANCE_M = 0.6`, `DOOR_CLEARANCE_M = 0.9`, функция
`_place_along_perimeter`
**Что упрощено:** мебель расставляется вдоль периметра по очереди с
фиксированными отступами — не полноценный constraint-solver, не проверяет
реальные проходы между всеми предметами, не оптимизирует по площади.
**Чем заменить:** constraint-solver (например, на базе OR-Tools) с
целевой функцией (эргономика + вкус) вместо жадного алгоритма.

### 2.5 Цены на мебель — фиксированная таблица, не каталог
**Где:** `backend/app/export/pdf_export.py`, `PRICE_ESTIMATES_USD`,
`DEFAULT_PRICE_ESTIMATE_USD = 150`
**Что упрощено:** смета в PDF считается по грубым усреднённым ценам за
категорию (диван — $900 и т.п.), никак не привязанным к реальным
поставщикам/моделям.
**Чем заменить:** после появления каталога мебели (см. п. 4) — реальные
цены конкретных SKU.

### 2.6 Стили вариантов B/C зафиксированы, не персонализированы
**Где:** `backend/app/tasks/pipeline_tasks.py`, `DESIGN_VARIANTS`
**Что упрощено:** вариант A — стиль пользователя, но B и C всегда
"Japandi" и "Luxury" вне зависимости от контекста (бюджета, вкусов).
**Чем заменить:** LLM сам предлагает 2 альтернативных стиля, исходя из
анкеты (а не жёстко прописанные Japandi/Luxury).

### 2.7 Тесты не покрывают LLM-зависимые ветки
**Где:** `backend/tests/` — нет тестов на `room_detector.run`,
`interior_designer.run`, `furniture_planner._select_furniture_set`,
`architect.propose_suggestions/apply_suggestion`, `conversation.interpret`
**Что упрощено:** покрыты только чистые функции без сети (расстановка,
патчи, сборка сцены, ретраи, сегментация, PDF). Всё, что реально дёргает
Groq API, не тестировалось ни разу с настоящим ключом.
**Чем заменить:** мок-тесты (patch `complete_json`) + хотя бы несколько
интеграционных тестов с реальным `GROQ_API_KEY` (например, в CI как
отдельный необязательный job).

## 3. Рендер и 3D

### 3.1 Мебель — параметрические примитивы, не 3D-модели
**Где:** `backend/app/models/scene.py` (`model_ref: str | None = None`),
`backend/app/agents/furniture_planner/agent.py` (`model_ref=None`),
`frontend/components/SceneViewer.tsx` (`DraggableFurniture` рендерит
`boxGeometry`)
**Что упрощено:** весь MVP мебель — это цветной бокс нужного размера.
**Чем заменить:** курируемая библиотека GLTF-моделей (категория × стиль),
подключается через уже существующее поле `model_ref` — рендер-компонент
уже спроектирован под замену (см. комментарий в `FurnitureMesh`/
`DraggableFurniture`), достаточно проверять `model_ref` и грузить GLTF
вместо `boxGeometry`, если оно задано.

### 3.2 Материалы — маленькая захардкоженная палитра
**Где:** `frontend/components/SceneViewer.tsx`, `MATERIAL_COLORS` (4
значения: `oak_wood`, `grey_fabric`, `white`, `grey`) и
`MATERIAL_PRESETS` (6 пресетов для панели выбора)
**Что упрощено:** если LLM или пользователь укажет материал не из этого
списка — код просто использует строку как есть (авось это хекс-цвет),
иначе рендер будет некорректным.
**Чем заменить:** полноценная библиотека материалов (текстуры, а не
плоский цвет) — вместе с GLTF-мебелью (п. 3.1) имеет смысл делать одновременно.

### 3.3 Walk-режим — упрощённые коллизии
**Где:** `frontend/components/SceneViewer.tsx`, `WalkMovement`,
`buildWallObstacles`, `collidesAt`, `PLAYER_RADIUS = 0.3`
**Что упрощено:** коллизии только со стенами (осевое скольжение по
прямоугольникам-препятствиям), НЕ с мебелью и декором — можно пройти сквозь
диван. Камера — просто круг радиусом 0.3м, не честная физика.
**Чем заменить:** добавить мебель в список препятствий (те же bounding
box, что уже есть в `FurnitureItem.dimensions`), при желании — честный
физический движок (cannon-es/rapier) вместо ручной проверки.

### 3.4 PDF-экспорт — 2D-схема, не 3D-рендер
**Где:** `backend/app/export/pdf_export.py`, `_draw_floor_plan_schematic`
**Что упрощено:** в PDF — плоская схема сверху (прямоугольники комнат и
мебели), не изображение 3D-сцены.
**Чем заменить:** рендер сцены на бэкенде (headless Three.js/Puppeteer
скриншот) и вставка PNG в PDF вместо векторной схемы.

## 4. Инфраструктура и безопасность

### 4.1 Нет авторизации
**Где:** везде — ни одного auth-эндпоинта/middleware
**Что упрощено:** любой, кто знает `project_id`, может читать/менять
проект. Осознанно исключено из MVP по ТЗ ("Без регистрации").
**Чем заменить:** Supabase Auth / Clerk / свой JWT — на усмотрение, когда
понадобится реальные пользователи и приватность проектов.

### 4.2 Каталога мебели нет
**Где:** нигде не реализовано (сознательно исключено из MVP по ТЗ)
**Что упрощено:** мебель выбирает LLM "из головы", у пользователя нет
возможности выбрать конкретную модель/поставщика.
**Чем заменить:** отдельный сервис каталога (реальные SKU, цены, GLTF-модели
— завязано на п. 3.1 и п. 2.5).

### 4.3 CORS и MinIO — значения для локальной разработки
**Где:** `backend/app/core/config.py` (`cors_allow_origins = ["http://localhost:3000"]`),
`backend/.env.example` (`S3_ACCESS_KEY=minioadmin`, `S3_SECRET_KEY=minioadmin`)
**Что упрощено:** дефолты рассчитаны только на локальный docker-compose.
**Чем заменить:** в проде — реальные домены в CORS, реальные креды для
S3/R2 через секреты (не коммитить в `.env`).

### 4.4 WebSocket без переподключения
**Где:** `frontend/lib/store.ts`, `connectWebSocket`, `socket.onclose`
**Что упрощено:** при разрыве соединения (`onclose`) сокет просто
обнуляется — нет автоматического reconnect. Пользователь продолжит
получать статус только через ручной поллинг (`refreshProject` в
`app/page.tsx` и так подстраховывает раз в 3 секунды, но WS-часть перестаёт
работать до перезагрузки страницы).
**Чем заменить:** reconnect с backoff в `onclose`.

### 4.5 Taskiq scheduler создан, но не используется
**Где:** `backend/app/tasks/broker.py`, переменная `scheduler`
**Что упрощено:** `TaskiqScheduler` инициализирован "про запас" — нет ни
одной периодической задачи, которая бы через него запускалась.
**Чем заменить:** либо использовать (например, для периодической очистки
старых версий сцен), либо убрать, чтобы не вводить в заблуждение.

### 4.6 Нет rate limiting
**Где:** нигде — ни на `/projects/upload`, ни на `/chat`
**Что упрощено:** ничего не мешает засыпать сервер запросами (в т.ч.
дорогими — каждый апload запускает CV + 3 параллельных LLM-пайплайна).
**Чем заменить:** slowapi/nginx-уровень лимитов на IP или проект.

### 4.7 Фронтенд-тестов нет вообще
**Где:** `frontend/` — ни одного `*.test.tsx`, Jest/RTL не настроены
**Что упрощено:** только backend покрыт тестами (23 шт.), вся клиентская
логика (стор, компоненты) не тестируется автоматически.
**Чем заменить:** Vitest/Jest + React Testing Library хотя бы для
`lib/store.ts` и логики коллизий в `SceneViewer.tsx`.

## Как этим пользоваться

Каждый пункт независим — можно заменять по одному, не трогая остальное,
кроме явно указанных связок (например, 3.1 и 3.2 логично делать вместе;
2.5 зависит от 4.2). Если возьмёшься за что-то из списка — могу помочь
сразу с конкретным пунктом.
